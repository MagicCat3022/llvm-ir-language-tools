# Offline library help research

Researched 2026-09-10 from primary documentation. `src/library.js` contains 44 original-prose entries: 20 C-library functions and 24 LLVM intrinsic families. The catalog is documentation, not executable declarations or an ABI database.

## C library references and pitfalls

- [POSIX formatted output](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fprintf.html): shared printf/fprintf/sprintf/snprintf specification, conversion meanings, flags, dynamic width/precision, length modifiers, counts and errors. `snprintf` reports the required output count, excluding the terminator, rather than necessarily the stored count. A field width is not a buffer capacity. Overlap is invalid for formatted buffer output. `%n` writes memory. Locale and positional formats are not universal C features.
- [GNU libc variadic calls](https://www.gnu.org/software/libc/manual/html_node/Calling-Variadics.html): default integer promotions and float-to-double promotion. The help explains that LLVM IR must already carry the correct promoted arguments; opaque pointers and integer widths do not identify C source types. `%ld` means C long, `%zu` size_t, and LP64/LLP64 differ. The extension does not select a data model or synthesize target-specific signatures.
- [POSIX formatted input](https://pubs.opengroup.org/onlinepubs/9799919799/functions/fscanf.html): input receives destination pointers; `%f` and `%lf` need different pointees. `*` suppresses assignment rather than reading a width argument; `%n` is excluded from assignment counts. `%c` does not append a terminator. Bounded `%s`/`%[` still need extra terminator storage. EOF, matching failure and assignment counts differ. Numeric overflow is not a recoverable format-checking guarantee.
- [puts](https://pubs.opengroup.org/onlinepubs/9799919799/functions/puts.html), [putchar](https://pubs.opengroup.org/onlinepubs/9799919799/functions/putchar.html): puts appends a newline and returns a nonnegative success indicator, not a guaranteed byte count; putchar writes a converted byte.
- [malloc](https://pubs.opengroup.org/onlinepubs/9799919799/functions/malloc.html), [calloc](https://pubs.opengroup.org/onlinepubs/9799919799/functions/calloc.html), [realloc](https://pubs.opengroup.org/onlinepubs/9799919799/functions/realloc.html), [free](https://pubs.opengroup.org/onlinepubs/9799919799/functions/free.html): allocation failure and zero-size behavior must not be conflated. For nonzero realloc size, failure preserves the original allocation. Successful realloc invalidates old pointers even if the address happens not to change. calloc initializes bits; not every target represents every null pointer or floating zero as all-zero bits. Fundamental alignment is not arbitrary over-alignment.
- [memcpy](https://pubs.opengroup.org/onlinepubs/9799919799/functions/memcpy.html), [memmove](https://pubs.opengroup.org/onlinepubs/9799919799/functions/memmove.html), [memset](https://pubs.opengroup.org/onlinepubs/9799919799/functions/memset.html): overlap differs; these routines do not validate capacities. memset fills bytes, not typed elements, and does not promise secure erasure.
- [strlen](https://pubs.opengroup.org/onlinepubs/9799919799/functions/strlen.html), [strcmp](https://pubs.opengroup.org/onlinepubs/9799919799/functions/strcmp.html): byte counts/order rather than Unicode character counts or locale collation; only strcmp's result sign is portable.
- [exit](https://pubs.opengroup.org/onlinepubs/9799919799/functions/exit.html), [abort](https://pubs.opengroup.org/onlinepubs/9799919799/functions/abort.html): normal cleanup differs from abnormal termination. Do not depend on abort flushing buffered output.

## Intrinsic references and pitfalls

- [llvm.memcpy](https://llvm.org/docs/LangRef.html#llvm-memcpy-intrinsic), [llvm.memmove](https://llvm.org/docs/LangRef.html#llvm-memmove-intrinsic), [llvm.memset](https://llvm.org/docs/LangRef.html#llvm-memset-intrinsics): void return, length overload, address-space-qualified pointers and scalar volatile flag. Modern memcpy intrinsic permits equal or non-overlapping ranges, unlike libc memcpy's overlap contract. Zero length does not override parameter attributes. Legacy typed-pointer overloads such as `.p0i8` remain recognized.
- [inline memcpy](https://llvm.org/docs/LangRef.html#llvm-memcpy-inline-intrinsic) and [element-wise atomic memcpy](https://llvm.org/docs/LangRef.html#llvm-memcpy-element-unordered-atomic-intrinsic) have materially different constraints. This catalog deliberately rejects these distinct families rather than assigning ordinary memcpy documentation. The same exclusion applies to other inline/atomic memory variants.
- [Current lifetime start](https://llvm.org/docs/LangRef.html#llvm-lifetime-start-intrinsic), [current lifetime end](https://llvm.org/docs/LangRef.html#llvm-lifetime-end-intrinsic), [LLVM 20 lifetime start](https://releases.llvm.org/20.1.0/docs/LangRef.html#llvm-lifetime-start-intrinsic): current signatures are unsuffixed and take one pointer; historical signatures take size and pointer, often with `.p0`/`.p0i8`. A lifetime marker is not heap allocation or freeing. Help explicitly labels version-dependent arguments.
- [Debug records](https://llvm.org/docs/SourceLevelDebugging.html#debug-records), [legacy dbg.value](https://llvm.org/docs/SourceLevelDebugging.html#llvm-dbg-value), [legacy dbg.declare](https://llvm.org/docs/SourceLevelDebugging.html#llvm-dbg-declare): modern `#dbg_value`/`#dbg_declare` records are not ordinary call instructions. Catalog entries apply to the older three-metadata-argument intrinsic declarations, with links explaining the distinction.
- [assume](https://llvm.org/docs/LangRef.html#llvm-assume-intrinsic), [expect](https://llvm.org/docs/LangRef.html#llvm-expect-intrinsic), [expect.with.probability](https://llvm.org/docs/LangRef.html#llvm-expect-with-probability-intrinsic): an assumption affects correctness; an expectation is only a hint and returns the actual value. Expect overloads are scalar integers, not arbitrary vectors.
- [trap](https://llvm.org/docs/LangRef.html#llvm-trap-intrinsic), [debugtrap](https://llvm.org/docs/LangRef.html#llvm-debugtrap-intrinsic): a terminating trap differs from requesting debugger attention; debugtrap is not inherently noreturn.
- [ctpop](https://llvm.org/docs/LangRef.html#llvm-ctpop-intrinsic), [ctlz](https://llvm.org/docs/LangRef.html#llvm-ctlz-intrinsic), [cttz](https://llvm.org/docs/LangRef.html#llvm-cttz-intrinsic), [bswap](https://llvm.org/docs/LangRef.html#llvm-bswap-intrinsics): ctlz/cttz's zero flag is scalar even for vector inputs; zero can yield poison. Bswap widths must be positive multiples of 16, not just multiples of eight, and lane order is unchanged.
- [sqrt](https://llvm.org/docs/LangRef.html#llvm-sqrt-intrinsic), [fabs](https://llvm.org/docs/LangRef.html#llvm-fabs-intrinsic): source types and fast-math flags govern semantics. Sqrt has no errno/trapping behavior like libm may have; fabs preserves non-sign bits, including NaN payload. Constrained/VP/other prefixed families are not accidentally matched.
- [Signed add overflow](https://llvm.org/docs/LangRef.html#llvm-sadd-with-overflow-intrinsics), [unsigned add](https://llvm.org/docs/LangRef.html#llvm-uadd-with-overflow-intrinsics), [signed sub](https://llvm.org/docs/LangRef.html#llvm-ssub-with-overflow-intrinsics), [unsigned sub](https://llvm.org/docs/LangRef.html#llvm-usub-with-overflow-intrinsics), [signed mul](https://llvm.org/docs/LangRef.html#llvm-smul-with-overflow-intrinsics), [unsigned mul](https://llvm.org/docs/LangRef.html#llvm-umul-with-overflow-intrinsics): return a struct with wrapped result and overflow flag; vectors require a corresponding vector of i1 flags.

## Conservative matching and intentional limits

`lookupLibrary(name, symbol)` only attaches help to compatible function declarations, not definitions, aliases, internal/private functions, non-C calling conventions or ABI-transforming parameter attributes. Libc requires the expected parameter count, variadicness, basic pointer/integer categories and return category. Int-sized libc positions support i16/i32/i64; size positions support i16/i32/i64/i128. This is deliberately a basic shape gate, not a proof that a symbol resolves to libc. A compatible external name may still resolve to a custom implementation; the UI should prefer a known workspace implementation and suppress library annotation for it. Every libc entry therefore explicitly says the actual declaration and target govern ABI.

Quoted and hex-escaped names compare by LLVM identifier bytes. Bare numbered symbols, leading `\01`, platform underscore decorations, version suffixes, case changes, wrapper names such as `__printf_chk`, and guessed/malformed overloads are rejected. No platform/mangling prefixes are stripped.

Intrinsic suffixes are fully anchored and declaration types are compared to them. Integer width is capped at LLVM's 8,388,607-bit bound; address spaces at 16,777,215; catalog vector counts at a conservative 1,048,576 lanes. Fixed and scalable integer/floating vectors are supported for the documented families. Unsupported type spellings or counts produce no help rather than invented semantics. A catalog family name is a display/search key, not an executable overloaded declaration.

No online requests occur at runtime. No signature synthesis, automatic declarations, libc navigation, format-string validation or complete target/version compatibility validation is claimed. Existing LLVM diagnostics remain responsible for verifying actual IR.

## Verification

`node --test test/library.test.js` passes 12 tests covering behavior, printf/scanf differences, safe identity/signature guards, historical and modern spellings, overload lookalikes and catalog immutability. Live retrieval verified HTTP success for all 17 distinct primary pages used by the catalog and the existence of every intrinsic anchor on 2026-09-10. Tests themselves require no network.
